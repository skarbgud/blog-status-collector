# blog-stat-collector

내 네이버 블로그의 일별 유입경로와 검색어를 매일 모아 H2에 쌓고, 로컬 대시보드에서 한눈에 보는 도구.
네이버 블로그 통계에는 공개 API가 없어서, 한 번 수동 로그인한 세션으로 통계 화면이 내부적으로 부르는 JSON API를 직접 호출한다.

Java 17 · Spring Boot 3.5 · Spring Data JPA · H2 · Playwright for Java · JUnit 5

## 구조

```
 [login] 사람이 브라우저에서 직접 로그인 → 쿠키 파일 저장
                │
 [schedule]  매일 03:10 + 시작 직후 보충    ┐
 [collect]   기간 지정 수집                 ├─ 쓰기 ─▶ H2 파일 DB (data/blogstat)
 [collect-queries] 검색어만 30일 등 길게     ┘              │ 쓰기가 끝날 때마다
                                                          ▼ SCRIPT로 내보내기 (원자적 교체)
                                              data/replica/snapshot.sql
                                                          │ 파일이 바뀌면 다시 올림
 [dashboard] 127.0.0.1:8080 ◀─ 읽기 ─ 인메모리 H2 ◀────────┘
```

## 설계 결정과 이유

**DOM 대신 내부 JSON API.** 먼저 탐색 모드로 화면이 부르는 XHR을 모두 기록했고, `/api/blog/daily/referer/total`(유입처)과 `/total/detail`(검색어)을 찾았다. 화면 구조가 바뀌어도 덜 깨지고 브라우저 페이지를 띄울 필요도 없다(`context.request()`로 바로 호출).

**응답을 믿지 않고 검증한다.** 응답 `rows`는 행이 아닌 컬럼별 배열이다. 파싱한 방문수의 합이 `refererTotalCount`와 같은지 확인하고, 검색어 합이 유입처 방문수와 다르면 일부만 받은 것으로 보고 경고한다.

**재시도는 실패 종류별로.** 타임아웃, 429, 502/503/504는 지수 백오프 + 풀 지터(기본 1초, 최대 30초, 3회)로 재시도하고 429는 `Retry-After`를 따른다. 401/403은 세션 만료라 재시도해도 소용없으니 바로 중단하고 재로그인을 안내한다. 그 밖의 4xx는 요청이 잘못된 것이라 재시도하지 않는다.

**저장은 멱등.** 날짜 단위 트랜잭션에서 그 날짜를 지우고 다시 넣는다. 같은 날짜를 몇 번 수집해도 결과가 같다. 집계 중인 오늘 데이터는 저장하지 않는다.

**읽기/쓰기 분리.** H2 파일 DB는 한 프로세스만 열 수 있어서, 수집과 대시보드를 함께 켜면 잠금 충돌이 났다. 대안으로 H2 `AUTO_SERVER`가 있었지만 `sa`/빈 비밀번호의 TCP 포트를 모든 인터페이스에 열어 개인 통계가 네트워크에 노출되므로 쓰지 않았다. 대신 쓰기 쪽이 스냅샷을 내보내고, 대시보드는 그 스냅샷을 인메모리 DB에 올려 읽는다. 대시보드는 원본을 바꿀 수 없고 재시작 없이 새 데이터를 반영한다. 상주 스케줄러도 쉬는 동안에는 커넥션 풀을 비워 파일 잠금을 풀어 준다.

**세션.** Playwright persistent profile만으로는 네이버 로그인이 다음 실행에 남지 않았다. 그래서 로그인 직후 쿠키를 파일로 저장하고 수집 때 복원한다. 쿠키 만료일로 남은 일수를 계산해, 7일 이내면 로그와 대시보드 배너로 알린다.

**하지 않기로 한 것.** ID/PW 자동 입력과 캡차 우회는 하지 않는다. 본인 통계만, 하루 한 번, 요청 사이에 2~5초를 두고 수집한다. 대시보드는 `127.0.0.1`에만 바인딩한다.

## 실행

| 하는 일 | 스크립트 (Windows) |
|---|---|
| 로그인 (수동, "로그인 상태 유지" 체크) | `scripts\login.cmd` |
| 매일 자동 수집 (상주) | `scripts\scheduler.cmd` |
| 검색어만 길게 수집 (기본 30일, 받은 날짜는 건너뜀) | `scripts\collect-queries.cmd [일수] [--force]` |
| 대시보드 http://127.0.0.1:8080 | `scripts\dashboard.cmd` |

그 밖의 모드(`collect --from --to`, `publish`, `explore`)와 세부 규칙은 [CLAUDE.md](CLAUDE.md)에 있다.

## 테스트

`./gradlew test`, 100개. 파서는 실제 응답을 저장한 픽스처로 검증하고, 저장 멱등성과 검색어 합치기는 `@DataJpaTest`로, 스냅샷 내보내기/다시 올리기는 왕복 테스트로, 대시보드 프로필은 실제로 띄우는 스모크 테스트로 확인한다. 이 스모크 테스트가 Spring이 생성자를 고르지 못해 대시보드가 뜨지 않던 결함을 잡았다.
